# 第12回：クラウド同期の土台（DB・RLS・手動同期）

第10回の設計（`cloud-sync-design.md`）のうち、第12回で実際に作った部分をまとめる。
**この回でも、データの正本は利用者の端末（localStorage）。** クラウドは「同期先」であり、
自動では一切やりとりしない。

## 1. 作ったもの

| 種類 | ファイル | 内容 |
|---|---|---|
| DB | `supabase/migrations/20260926000001_cloud_sync.sql` | 5つのテーブル・制約・RLS（何度実行しても同じ結果） |
| DB確認 | `supabase/verify-rls.sql` | RLS が効いているかを確認する SQL（読み取りだけ） |
| 変換 | `src/cloud/cloudRows.ts` | 端末のデータ ⇄ クラウドの行。件数の数え方、内容比較用の指紋 |
| 判断 | `src/cloud/cloudSync.ts` | 「保存してよいか」「取得してよいか」の判断（通信しない純粋な関数） |
| 通信 | `src/cloud/cloudRepository.ts` | Supabase への読み書き。localStorage には一切触れない |
| 画面 | `src/components/CloudSyncSection.tsx` | 件数の表示・プレビュー・確認・実行 |

## 2. テーブル構成

すべての表に `user_id`（= `auth.uid()`）を持たせ、主キーに含める。
端末側のID（`P001` / `S001` / `R001`）はそのまま使う。**主キーが `(user_id, id)` なので、
別の利用者と同じIDがあっても衝突しない。**

| テーブル | 主キー | 端末側の対応 | 備考 |
|---|---|---|---|
| `products` | `(user_id, id)` | `products[]` | `unit_amount` / `target_unit_price` / `archived` など |
| `stores` | `(user_id, id)` | `stores[]` | |
| `price_records` | `(user_id, id)` | `priceRecords[]` | `recorded_at` = 端末の `createdAt`、`seq` も保持 |
| `shopping_items` | `(user_id, product_id)` | `shoppingList[]` + `purchased[]` | `purchased` 列で購入済みを表す |
| `user_settings` | `(user_id)` | `counters` + `version` | 利用者ごとに1行。`last_synced_at` も持つ |

外部キーにも `user_id` を含めている（`price_records → products` / `stores`、`shopping_items → products`）。
このため、**他人の商品・店舗を参照することが構造上できない。**

## 3. RLS（行レベルセキュリティ）

5つのテーブルすべてで RLS を有効にし、`authenticated`（ログイン済み）だけに
`select` / `insert` / `update` / `delete` の4つのポリシーを作る。条件はいずれも

```
auth.uid() = user_id          -- 読むとき（using）
auth.uid() = user_id          -- 書くとき（with check）
```

- 未ログイン（`anon`）ではポリシーが1つも当たらないため、**1行も読めず、1行も書けない**
- `user_id` を他人のIDにして送っても、`with check` で拒否される
- `service_role` キーは RLS を無視できるため、**ブラウザ側では絶対に使わない**（アプリ側にも誤設定の検出処理がある）

## 4. 端末 → クラウド（保存）

1. 「クラウドの状態を確認」でクラウド側の件数を取得
2. 「この端末のデータをクラウドへ保存」でプレビューを表示（この端末の件数／クラウドの件数／何が起きるか）
3. クラウドに別の内容がある場合は、チェックを入れるまで実行できない
4. 実行すると、クラウド側の自分の行を消してから、この端末の内容を入れ直す（500件ずつ分割）
5. **端末のデータは変更しない**

## 5. クラウド → 端末（取得）

1. プレビューで件数を確認（「クラウドと内容を見比べる」で同じかどうかも分かる）
2. この端末にデータがある場合は、**バックアップファイルを保存するまで実行できない**
3. チェックを入れて実行すると、クラウドのデータを検証（`loadAppData`）してから `repository.restore()` で置き換える
4. `restore()` は「1つ前の状態に戻す」用の退避を残すので、**直後なら1段階戻せる**

## 6. データを失わないための決まり

| 状況 | 保存（端末→クラウド） | 取得（クラウド→端末） |
|---|---|---|
| 両方データなし | できない（送るものがない） | できない（取るものがない） |
| この端末だけデータあり | 確認なしで実行できる | **できない**（端末のデータが消えるため） |
| クラウドだけデータあり | **できない**（クラウドのデータが消えるため） | 確認なしで実行できる |
| 両方データあり・内容が違う | チェックを入れて実行 | バックアップ＋チェックを入れて実行 |
| 両方データあり・内容が同じ | 確認なしで実行できる（変化なし） | 確認なしで実行できる（変化なし） |

さらに、

- 取得の直前にもう一度クラウドの中身を確認し、空だったら中止する（二重の歯止め）
- 通信が失敗しても端末のデータには一切触れない
- 自動マージ（内容の合成）はしない。どちらを残すかは必ず利用者が選ぶ

## 7. まだやっていないこと（第13回以降）

- 自動同期・バックグラウンド同期
- 項目単位の差分同期・競合の自動解決（Last Write Wins の本格導入）
- 削除の同期（tombstone）
- オフライン時の同期キュー
- 複数ユーザーでの共有
